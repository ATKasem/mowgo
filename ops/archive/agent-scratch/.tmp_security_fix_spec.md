## CRITICAL

### C1. invite-crew.js — cross-business account takeover (Flow 2)
**File:** `functions/api/invite-crew.js` (Flow 2, lines ~78-149)
**Bug:** When the invited email maps to an EXISTING user, the function PATCHes their profile `{business_id: ownerId, role:'crew', tier:'crew'}` with NO check that the target is not already an owner / member of another business.
**Fix:**
1. After fetching `existingProfiles[0]`, reject with 409 `{error: 'This user already belongs to a business'}` if `existingProfile.business_id` is set (non-null) OR `existingProfile.role === 'owner'`.
2. Only allow the overwrite when the existing user has `business_id == null` (free, unaffiliated user).
3. Keep the rest of Flow 2 identical.

### H1. invite-crew.js — HTML injection in invite email
**File:** `functions/api/invite-crew.js:233`
**Fix:** Add an `escapeHtml(str)` helper (copy the one from `functions/api/route-audit.js:24-26`) and wrap `ownerProfile.business_name` at line 233: `escapeHtml(ownerProfile.business_name || 'Your crew lead')`. Also wrap the `${resetUrl}` in the href ONLY if safe (it comes from Supabase admin generate_link — keep as-is; it's https). Escape business_name only.

### H2. invite-crew.js — no rate limiting + no tier gate
**Fix:**
1. Add in-memory per-IP + per-owner rate limiting (pattern from `functions/api/booking.js:15-37`): e.g. 10 invites per 15 min per authenticated owner id. Return 429 `{error:'Too many invitations. Please try again later.'}`.
2. Require inviter tier: the owner-profile query at line 60 currently selects `id,business_name,role`. Add `tier`. After the role check, reject 403 unless `tier` is `'crew'` OR `'premium'` (owner role + paid plan can invite). Message: `{error:'Crew invitations require a Crew or Premium plan'}`.

Add the dependency `androidx.security:security-crypto:1.1.0-alpha06` (or latest stable 1.1.x) to `app/build.gradle.kts` deps (check libs.versions.toml convention used in this repo). Wire it in `SupabaseClient.kt` inside `install(Auth) { sessionManager = ... }`. Read the supabase-kt 3.0.1 SessionManager interface from the jar/源码 (methods: saveSession/loadSession/deleteSession — exact names from `SessionManager.kt`) and implement all methods, storing the serialized UserSession JSON string. ### M5. Job photos in PUBLIC storage bucket
**Files:** uploaders: `client/android-native/app/src/main/java/com/mowgo/app/data/JobPhotoRepository.kt`, iOS equivalent in `ios-native/MowGo/Services/DataStore.swift` (search `job-photo` / photo upload), web: check `client/src/` for photo upload/display.
**Fix:**
1. NEW migration `supabase/migrations/020_storage_photo_rls.sql`:
   ```sql
   -- job-photo bucket: photos are private to the owning user
   CREATE POLICY "job-photo: owner select" ON storage.objects FOR SELECT
     USING (bucket_id = 'job-photo' AND (storage.foldername(name))[1] = (auth.uid())::text);
   CREATE POLICY "job-photo: owner insert" ON storage.objects FOR INSERT
     WITH CHECK (bucket_id = 'job-photo' AND (storage.foldername(name))[1] = (auth.uid())::text);
   CREATE POLICY "job-photo: owner update" ON storage.objects FOR UPDATE
     USING (bucket_id = 'job-photo' AND (storage.foldername(name))[1] = (auth.uid())::text);
   CREATE POLICY "job-photo: owner delete" ON storage.objects FOR DELETE
     USING (bucket_id = 'job-photo' AND (storage.foldername(name))[1] = (auth.uid())::text);
   ```
   (Guard with DROP POLICY IF EXISTS first.)
2. Clients must fetch photos AUTHENTICATED: change uploaders/readers to use Supabase Storage with auth (supabase-kt `storage.from("job-photo")` with auth session, or signed URLs). Web: check how photos are displayed (search `photoUrl`/`photo_url` in client/src) and if displayed via raw public URL, switch to authenticated download or signed URL via `supabase.storage.from('job-photo').createSignedUrl(path, 3600)`. iOS: use the SupabaseStorage module if available, else construct URL with the auth token header.
   - IMPORTANT: verify every place a photo URL is rendered and make reads authenticated; do not break existing photos for the owner/crew (owner id = first path segment, crew can only see their OWN userId path segment — acceptable per current data model where photos live under the creating user's id; if crew needs to view owner photos, that's a product change — do NOT expand policy beyond owner).
3. If the bucket currently exists WITHOUT RLS and files are public, note in code comment that existing objects remain but new policy gates access.
