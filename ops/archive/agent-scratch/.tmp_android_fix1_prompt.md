## HIGH — fix first

### H1. LeadPatch null serialization wipes columns on update (LeadRepository.kt, updateLead ~line 47-66)
`update(stamped)` serializes the full LeadPatch object; kotlinx.serialization default (`explicitNulls=true`, no custom Json config in repo) sends `null` for every unset field, and PostgREST sets those columns to NULL. Calling `updateLeadStatus(id, WON)` wipes name/phone/email/address/source/notes/clientId.
**Fix:** Build a `Map<String, Any>` containing ONLY the non-null fields of the patch (mirror the `mapOf(...)` pattern used in JobRepository for partial updates), always include `updated_at`, and pass that map to `.update(fields) { filter { eq("id", id) } }`. Example: `val fields = buildMap<String, Any> { stamped.name?.let { put("name", it) }; stamped.phone?.let { put("phone", it) }; stamped.email?.let { put("email", it) }; stamped.address?.let { put("address", it) }; stamped.source?.let { put("source", it) }; stamped.notes?.let { put("notes", it) }; stamped.status?.let { put("status", it) }; stamped.clientId?.let { put("client_id", it) }; put("updated_at", stamped.updatedAt!!) }`. Then keep the re-fetch (`decodeList<Lead>().firstOrNull()`) as the return.

### H2. Crew members see empty client list (InvoiceRepository.kt, loadClients ~line 16-20)
`ClientsViewModel` now calls `invoiceRepository.loadClients()` which filters by `user_id = currentUser.id` only. Crew members' `user_id` owns no clients (clients belong to `business_id` owner), so crew sees an empty list. `JobRepository.loadClients()` (line 61-76) already handles this correctly.
**Fix:** Mirror JobRepository.loadClients(): load `ProfileRepository().loadProfile()`, compute `val ownerId = if (profile?.role == "crew") profile.businessId else userId`, return emptyList() if ownerId null, filter by `eq("user_id", ownerId)`.

## MED

### M1. rainDelay moves in_progress jobs — iOS moves scheduled only (JobRepository.kt ~line 210, 214, 237)
iOS `DataStore.swift:1051` filters `$0.status == .scheduled` only. Android filters `scheduled || in_progress`. A job being actively worked on gets moved to another day.
**Fix:** Change both filters (demo + live) to `it.status == Job.STATUS_SCHEDULED` only. Also update the dialog helper text in TodayScreen.kt line ~296: "Only today's scheduled and in-progress jobs move." → "Only today's scheduled jobs move."

### M2. Rain delay history key not user-scoped (SettingsRepository.kt line 19)
Web uses `mowgo_rain_delay_history_${userId}` and iOS uses `rainDelayHistory_{userId}`; Android uses device-global `"rain_delay_history"`. Switching accounts on a shared device shows the previous user's history.
**Fix:** Make `RainDelayHistoryStore` derive a per-user key. The store methods (`load`, `add`, `replace`, `save`) should accept the current user id (or the store should resolve it via `SupabaseClientProvider.auth.currentSessionOrNull()?.user?.id`) and use key `stringPreferencesKey("rain_delay_history_$userId")`. In demo mode (not configured) use `"rain_delay_history_demo"`. Check TodayViewModel call sites and pass/resolve the userId accordingly. Do NOT make the key a constructor-time constant — resolve per call so account switches take effect.

### M3. RainDelayHistoryStore.add() read-modify-write race (RainDelayHistoryStore.kt lines 21-24)
`add()` does `load()` (one DataStore transaction) then `save()` (another). Two concurrent adds lose one entry.
**Fix:** Do the read+write atomically inside ONE `context.dataStore.edit { prefs -> ... }` block: read `prefs[key]`, decode, prepend, cap at 50, encode, write. Same for `replace()`. `load()` can stay as-is (read-only) but must use the same user-scoped key.

### M4. Sign-out does not clear rain delay history (SettingsRepository.kt clearNotificationPrefs ~line 29-35, MoreViewModel.kt line 182)
`clearNotificationPrefs()` removes completion + rain keys but not the rain delay history key, so history leaks to the next account.
**Fix:** Also remove the rain_delay_history key(s) there. Since the key is now user-scoped, remove the current user's key (resolve userId in the same way as M2) — and in demo mode the demo key. If resolving userId is awkward there, remove ALL keys whose name starts with `rain_delay_history` by iterating `prefs.asMap().keys.filter { it.name.startsWith("rain_delay_history") }`.

### M5. convertLeadToClient swallows client-rollback failure (LeadRepository.kt ~line 105-108)
If `updateLead` fails after `createClient` succeeds, `catch (_: Exception) { }` around `clientRepository.deleteClient(client.id)` swallows a failed cleanup, leaving a dangling client with no lead. iOS C2 fix surfaces this.
**Fix:** Don't fully swallow: capture the cleanup failure and include it in the rethrown error, e.g. `throw RuntimeException("Conversion failed: ${error.message}" + (cleanupError?.let { "; cleanup failed: ${it.message}" } ?: ""), error)`.

### M6. rainDelay rollback failures silently swallowed (JobRepository.kt rainDelay ~line 236-240)
The rollback loop `try { updateJobDate(...) } catch (_: Exception) { }` swallows per-job rollback failures; if some jobs revert and others don't, no webhook fires AND no error surfaces — inconsistent state with no signal. iOS R7-2/3 surfaces "rollback incomplete".
**Fix:** Track `var rollbackFailed = false` in the catch loop; after the loop, if rollbackFailed, throw a combined error: `throw RuntimeException("Rain delay rollback incomplete — verify your schedule (original: ${error.message})", error)`. (Do not fire the webhook in this path — already correct.)

## LOW

### L1. Webhook uses requested status instead of server-confirmed (LeadRepository.kt updateLeadStatus ~line 68-74)
Payload uses `status = status.value` (requested) instead of `updated.status` (server-confirmed after re-fetch). Web sends the confirmed row value.
**Fix:** `"status" to updated.status`.

### L2. client_id empty-string vs null mismatch in webhook (LeadRepository.kt line 72)
`client_id` is sent as `""` when null; web sends null/omits it. Consumers can't distinguish no-client from empty id.
**Fix:** Build the payload map conditionally — only include `client_id` when `updated.clientId != null` (use `buildMap { ... }`), same for any other nullable payload keys.

### L3. rainDelay targetDate format not validated (JobRepository.kt rainDelay, and undoRainDelay comparison)
Undo compares `job.scheduledDate != entry.targetDate` by exact string; a non-ISO targetDate would never match. Web validates ISO.
**Fix:** At the top of `rainDelay(date: String, targetDate: String)` add `require(targetDate.matches(Regex("\\d{4}-\\d{2}-\\d{2}")))` and `require(date.matches(Regex("\\d{4}-\\d{2}-\\d{2}")))`.

### L4. RainDelayDialog target date stale if dialog crosses midnight (TodayScreen.kt line 283, TodayViewModel confirmRainDelay)
`remember { mutableStateOf(tomorrow) }` captures tomorrow at dialog open; if the dialog stays open past midnight, `confirmRainDelay` computes `sourceDate = LocalDate.now()` (next day) while target is yesterday's tomorrow → jobs move backwards.
**Fix:** In `confirmRainDelay(targetDate: String)` in TodayViewModel, guard: if `LocalDate.parse(targetDate) <= LocalDate.now()` then set error state ("Rain delay target must be in the future") and return without mutating. Keep the dialog change minimal.

### L5. ClientsViewModel.mutate() has no re-entrancy guard (ClientsViewModel.kt ~line 110)
Two concurrent mutate() calls race: first completion resets isMutating=false while second still runs; loadData() inside fires concurrently.
**Fix:** At the top of mutate(): `if (_uiState.value.isMutating) return`. Ensure the guard is released in a finally-style path so a failure doesn't wedge the flag.
