### Pass 1 Finding Verification

#### CRIT-001: SQL Injection via Unsafe String Interpolation — **FALSE POSITIVE**
- **Pass 1 claim:** `.or(\`id.eq.${bizId},business_id.eq.${bizId}\`)` is SQL injection.
- **Actual code:** `data.js` lines 466, 618. The Supabase JS client's `.or()` method sends filter syntax to PostgREST, which parameterizes values via URL encoding. `bizId` comes from `profile.id` (a UUID set by the database trigger) or `profile.business_id` (set during invitation, immutable via RLS).
- **Verdict:** PostgREST does NOT execute raw SQL — it builds parameterized HTTP queries. This is filter syntax, not SQL. The values are constrained to UUIDs by the database schema. **Dismissed as CRITICAL; could be MEDIUM at most for theoretical PostgREST filter injection if a user could set a crafted business_id (they cannot).**

#### CRIT-002: Authentication Bypass in Edge Functions — **FALSE POSITIVE (Display Artifact)**
- **Pass 1 claim:** Template literal syntax error `***` in `{ Authorization: authHeader *** }` allows null/undefined auth.
- **Actual code:** Lines 32-36 of `create-payment-intent/index.ts`:
  ```typescript
  const authHeader = req.headers.get("Authorization") ?? "";
  const supabase = createClient(url, key, { global: { headers: { Authorization: authHeader } } });
  ```
  The `***` in the read_file output is a redaction/display artifact. The actual source code passes `authHeader` directly (which already includes the `Bearer` prefix from the request). The auth check at lines 44-48 correctly rejects unauthenticated requests.
- **Verdict:** **Dismissed.** No syntax error exists in the actual source.

#### CRIT-003: Payment Amount Tampering — **FALSE POSITIVE**
- **Pass 1 claim:** `Math.round(invoice.amount * 100)` relies on client-controlled amount.
- **Actual code:** `server/index.js` lines 364-376:
  ```javascript
  // Fetch the invoice server-side — never trust client-provided amounts
  const { data: invoice } = await supabase.from('invoices')
    .select('amount, status, user_id').eq('id', invoice_id).single();
  const amountInCents = Math.round(invoice.amount * 100);
  ```
  The server fetches the amount from the database, not from the client request. The code even has a comment explaining this.
- **Verdict:** **Dismissed.** Server-side validation is correctly implemented.

#### CRIT-004: Race Condition in Payment Confirmation — **PARTIALLY TRUE (different bug)**
- **Pass 1 claim:** Update lacks atomic transaction, allowing double-payment.
- **Actual code:** `confirm-payment/index.ts` lines 148-158. The update WHERE clause includes `.eq("stripe_payment_intent_id", payment_intent_id)`, which acts as an optimistic lock. Two concurrent calls with the same payment_intent_id are idempotent — both succeed harmlessly.
- **However, there IS a real bug (see DEEP-001 below):** If `create-payment-intent` fails to save the payment_intent_id (line 136-140, error unchecked), then `confirm-payment`'s WHERE clause won't match, the update affects 0 rows, but the function still returns `{ success: true }`.
- **Verdict:** **Original claim dismissed.** Real bug documented as DEEP-001/DEEP-002.

#### HIGH-001: Business ID Authorization Bypass — **FALSE POSITIVE**
- **Actual code:** `data.js` line 460. While the client constructs `bizId` locally, all queries go through Supabase with RLS enforced. The RLS policies in `002_crew_features.sql` (lines 62-158) use `current_business_id()` — a `SECURITY DEFINER` function that computes the business owner's ID from the authenticated user's profile.
- **Verdict:** **Dismissed.** RLS provides defense-in-depth.

#### HIGH-002: Unsafe HTML Construction in Email Templates — **LOW SEVERITY (not HIGH)**
- **Actual code:** `server/index.js` lines 81-88, 334. The `escapeHtml()` function properly escapes `&`, `<`, `>`, `"`, and `'`. The `invoice_id` in the URL is a UUID (safe characters).
- **Verdict:** **Downgraded to LOW.** HTML escaping is solid.

#### HIGH-003: Insufficient Input Validation on Team Invitations — **LOW SEVERITY (not HIGH)**
- **Actual code:** `server/index.js` lines 122-125. The regex is basic but adequate. Supabase's `inviteUserByEmail()` validates server-side.
- **Verdict:** **Downgraded to LOW.**

#### HIGH-004: Weak Error Messages Expose Internal State — **TRUE (LOW SEVERITY)**
- **Actual code:** `data.js` lines 65, 214, 455, 469. Error messages include `error.message` from Supabase, visible in browser console.
- **Verdict:** **Confirmed but LOW.**

#### HIGH-005: Missing CSRF Protection — **FALSE POSITIVE**
- **Actual code:** JWT Bearer token auth. Browsers don't send Authorization headers cross-origin.
- **Verdict:** **Dismissed.**

#### HIGH-006: Stripe Key Exposure in Client-Side Logging — **FALSE POSITIVE**
- **Actual code:** Stripe SDK returns user-friendly error messages, not API keys.
- **Verdict:** **Dismissed.**

### New Findings — Deep Review

#### DEEP-001: create-payment-intent Silently Ignores Save Failure (HIGH)
**File:** `ios-native/edge-functions/create-payment-intent/index.ts` lines 136-140
**Severity:** HIGH

```typescript
// BUG: Error from this update is never checked
await supabase
  .from("invoices")
  .update({ stripe_payment_intent_id: paymentIntent.id })
  .eq("id", invoice_id)
  .eq("user_id", user.id);
```

**Problem:** The Stripe PaymentIntent is successfully created (money may be charged), but the `stripe_payment_intent_id` is saved via fire-and-forget. If this update fails, the payment intent exists at Stripe but is never recorded on the invoice. When `confirm-payment` runs, its WHERE clause `.eq("stripe_payment_intent_id", payment_intent_id)` won't match, causing a silent failure.

**Fix:**
```typescript
const { error: saveErr } = await supabase
  .from("invoices")
  .update({ stripe_payment_intent_id: paymentIntent.id })
  .eq("id", invoice_id)
  .eq("user_id", user.id);

if (saveErr) {
  console.error("Failed to save payment intent ID:", saveErr);
}
```

#### DEEP-002: confirm-payment Returns Success When 0 Rows Updated (HIGH)
**File:** `ios-native/edge-functions/confirm-payment/index.ts` lines 148-174
**Severity:** HIGH

```typescript
const { error: updateErr } = await supabase
  .from("invoices")
  .update({ status: "paid", ... })
  .eq("id", invoice_id)
  .eq("user_id", user.id)
  .eq("stripe_payment_intent_id", payment_intent_id);

if (updateErr) { ... error ... }

// BUG: No check on rows affected
return new Response(JSON.stringify({ success: true }), { status: 200, ... });
```

**Problem:** If the WHERE clause doesn't match (e.g., `stripe_payment_intent_id` was never saved), the update affects 0 rows and the function returns `{ success: true }`. The user sees "Payment confirmed" but the invoice remains unpaid.

**Fix:**
```typescript
const { data: updated, error: updateErr } = await supabase
  .from("invoices")
  .update({ status: "paid", paid_at: new Date().toISOString(), stripe_payment_intent_id: payment_intent_id })
  .eq("id", invoice_id)
  .eq("user_id", user.id)
  .eq("stripe_payment_intent_id", payment_intent_id)
  .select("id");

if (updateErr) { ... error ... }
if (!updated || updated.length === 0) {
  return new Response(JSON.stringify({ error: "Invoice not found or already paid" }), {
    status: 409, ...
  });
}
```

#### DEEP-003: create-checkout-session Doesn't Verify Customer Creation (MEDIUM)
**File:** `ios-native/edge-functions/create-checkout-session/index.ts` lines 84-105
**Severity:** MEDIUM

```typescript
const custResp = await fetch("https://api.stripe.com/v1/customers", { ... });
const customer = await custResp.json();
customerId = customer.id;  // BUG: No check that custResp.ok
```

**Problem:** If customer creation fails, `customer.id` is `undefined`. The code saves `undefined` to the profile and passes it to checkout session creation, which fails at Stripe.

**Fix:**
```typescript

  return new Response(JSON.stringify({ error: "Could not create customer" }), { status: 502, ... });
}
const customer = await custResp.json();
customerId = customer.id;
```

#### DEEP-005: Webhook Uses Floating-Point Comparison for Currency (MEDIUM)
